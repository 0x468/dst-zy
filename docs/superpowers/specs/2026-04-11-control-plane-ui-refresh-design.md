# DST 控制平面 UI 重设计方案

## 背景

当前 `control-plane/web` 已经具备可用的基础功能：

- 登录与会话恢复
- 集群列表与选中切换
- 创建 / 导入集群
- 集群启停、更新、校验、备份等操作入口
- 配置表单编辑
- 原始 `cluster.ini` 高级编辑
- 任务、审计、备份等记录面板

但前端仍处于“功能已接通、界面尚未设计”的阶段，主要问题不是局部样式粗糙，而是整套视觉与布局体系缺失：

- 没有全局样式入口和设计 token
- 页面结构基本是原生标签直接平铺
- 不同信息层级没有建立主次关系
- 操作按钮、表单、列表、日志面板缺少统一语言
- 页面更像开发期占位界面，而不是成熟控制台

因此需要一次明确范围内的 UI 重设计，把现有控制平面提升到“可长期使用的现代化运维控制台”水位。

## 目标

- 将控制平面升级为成熟、克制、专业的运维控制台视觉风格
- 在不修改后端 API 合约的前提下，重建前端布局、组件层级与样式系统
- 让用户进入页面后优先看到状态、关键连接信息和主要操作
- 让列表、表单、任务、审计、备份等区域具有明确的信息分区和一致的交互语言
- 为后续继续扩展控制台页面提供稳定的前端样式基础设施

## 非目标

- 不改变认证流程和后端接口协议
- 不在本轮引入新的业务功能
- 不在本轮重做前端路由结构
- 不在本轮引入沉重的 UI 组件库
- 不为了视觉重构而大规模拆碎现有文件

## 当前问题归纳

### 1. 缺少视觉系统

当前前端没有独立的全局样式文件，也没有颜色、间距、阴影、圆角、字体等统一 token。结果是：

- 页面默认浏览器观感明显
- 后续新增页面无法复用统一样式
- 不同组件很难形成产品级一致性

### 2. 信息架构不清晰

集群详情页虽然已经包含概览、配置、备份、任务、审计和高级编辑，但这些内容目前主要按实现顺序平铺，缺少运维场景下的阅读顺序：

1. 先看状态
2. 再执行动作
3. 再编辑常用配置
4. 最后排查历史记录和高级内容

### 3. 集群列表区缺少“控制台导航”质感

当前左侧区域本质是按钮列表加一个简单表单，缺少：

- 导航区域边界
- 选中态层级
- 状态可视化
- 创建 / 导入入口的独立区隔

### 4. 高级模式隔离不充分

原始文件编辑虽然已经存在，但视觉上还不够“高级模式”，容易让用户感知不到风险边界，也无法形成“日常操作区”和“原始编辑区”的明确分层。

## 选定方向

本轮 UI 采用用户确认的方向：`Steel Ops`

这是一个偏浅色主界面、搭配深石墨色导航和高对比状态区域的现代运维控制台风格，设计目标是：

- 专业而不过度花哨
- 稳定、清晰、适合长时间使用
- 保留“控制平面”的力量感，而不是普通 SaaS 后台模板

不采用强游戏皮肤路线，也不引入过多装饰性元素。页面气质以“运维中控台”优先。

## 视觉系统

### 色彩

整体采用三层色彩策略：

1. 主背景：冷灰白，不使用刺眼纯白
2. 导航与重点状态区：深石墨 / 深蓝灰
3. 功能状态色：使用清晰但克制的蓝、绿、橙、红

预期语义：

- `running`：冷绿色
- `stopped`：中性灰
- `pending` / `updating`：橙色或琥珀色
- `error` / 危险操作：红色
- 选中态与可交互强调：蓝绿色或冷蓝

### 字体

- 标题使用更硬朗、带控制台气质的无衬线字重
- 正文与表单使用清晰、中性的阅读字体
- 代码 / 原始配置区域使用等宽字体

目标不是“设计感字体秀”，而是让标题、正文、代码三种内容有明确区分。

### 形状与层级

- 圆角中等，避免过圆带来的消费级产品感
- 卡片使用清晰边框和轻阴影，不做强玻璃拟态
- 通过底色、边框、标题和间距建立层级，而不是靠复杂装饰

### 动效

只保留克制而有意义的动效：

- 页面首屏轻微淡入 / 上移
- 侧栏集群切换的短时状态反馈
- 按钮 pending 与标签切换的细微过渡

不做复杂炫技动画。

## 信息架构与页面骨架

### 登录页

登录页不再只是单个表单，而是明确做成“桌面双栏、窄屏单列”的品牌化入口：

- 桌面端左侧显示控制台名称、用途说明、简短能力摘要
- 桌面端右侧为登录卡片
- 窄屏下改为上信息、下表单的单列堆叠
- 登录卡片包含更明确的标题、副标题、字段说明与错误提示

目标是让用户一进页面就感知到这是 DST 控制平面，而不是默认脚手架登录框。

### 集群总览页骨架

已登录后的主界面采用三层结构：

### 1. 左侧固定导航栏

职责：

- 展示集群列表
- 展示当前集群选中态
- 提供创建 / 导入入口

视觉特征：

- 深色背景，与主工作区拉开层次
- 集群项显示名称、slug、状态点
- 选中项具有明显底色、高亮边界或状态线

创建 / 导入入口不再像附属表单堆在下方，而是固定为侧栏底部的独立操作卡片。卡片默认展示模式切换、主要字段和提交按钮，在窄屏下再折叠为展开区。

### 2. 顶部上下文栏

职责：

- 展示当前集群名称、备注、状态徽标
- 放置全局动作，如退出登录
- 在需要时展示最近同步 / 最近动作提示

顶部栏是工作上下文的固定入口，不承载过多业务内容。

### 3. 中央主工作区

分为两个模式：

- `Overview`
- `Advanced`

默认进入 `Overview`。这也是大多数用户的常用工作区。

## Overview 模式布局

### 概览摘要卡

页面最上方放置一组摘要卡，用于快速扫读：

- 集群状态
- Master / Caves 端口
- 集群名称 / 游戏模式等关键信息

这一区优先回答“这个集群现在是否健康、服务在哪些端口、我是否连接对了”。

### 生命周期控制面板

所有运维动作集中为一个主控制面板，而不是零散按钮：

- `Start`
- `Stop`
- `Restart`
- `Update`
- `Validate`
- `Backup`

控制面板要求：

- 主动作按钮视觉统一
- 危险动作和普通动作分层
- pending 状态明确
- 当后端返回错误时，可在面板内显示内联错误

### 常用配置面板

表单化配置编辑区采用标准卡片布局：

- 字段对齐
- 标签、辅助说明和输入框宽度统一
- 保存区域稳定，不随内容跳动
- 保存成功 / 失败有明确反馈

初期仍围绕现有字段：

- `clusterName`
- `clusterDescription`

后续新增字段时可继续复用该布局系统。

### 备份、任务、审计记录面板

这三类内容都属于“运维历史记录”，但呈现形式不完全相同：

- 备份：突出最近一次，旧备份次级展示
- 任务：强调任务类型、状态和输出摘录
- 审计：更适合时间线或事件流结构

面板之间应保持统一外观，但各自保留最适合的数据呈现样式。

### Danger Zone

删除集群必须单独放在 `Danger Zone`：

- 独立卡片
- 高风险配色
- 保持当前“输入 slug 确认”的行为约束

只有在集群停止状态下显示或可操作，继续尊重现有业务逻辑。

## Advanced 模式布局

`Advanced` 模式专门承载原始文件编辑：

- 视觉上更像编辑器工作区
- 使用等宽字体
- 强调“你正在直接编辑原始配置”
- 保留保存动作，但降低与普通表单的视觉相似度

目标是让用户心理上明确区分：

- `Overview` = 日常运维与常规配置
- `Advanced` = 底层原始文件编辑

## 组件级设计规则

### 按钮

按钮分为四种语义层级：

- 主动作
- 次动作
- 中性工具动作
- 危险动作

不同状态需要统一：

- 默认
- hover
- active
- disabled
- pending

### 表单

表单元素统一规则：

- 标签在上，输入框在下
- 错误信息紧贴字段或表单头部
- 辅助说明使用次级文本样式
- 输入控件高度、边框、焦点态统一

### 状态徽标

`running`、`stopped` 等状态不再只显示纯文本，应统一为徽标组件：

- 固定大小和圆角
- 配合状态点或图标
- 能在侧栏列表和详情页复用

### 面板 / 卡片

卡片应具备统一结构：

- 标题区
- 内容区
- 可选工具区
- 可选底部动作区

这样后续新增更多管理模块时不需要重新定义布局语言。

## 响应式策略

本轮主目标仍是桌面端运维使用，但必须保证窄屏可用：

- 宽屏下：侧栏 + 主工作区并排
- 中等宽度下：卡片可两列或单列重排
- 较窄宽度下：侧栏切换为顶部块或折叠区，主工作区单列显示

不追求移动端 App 级体验，但至少保证笔记本和较窄浏览器宽度下不破版。

## 实现边界

### 保持不变

- 所有后端 API path 与 payload
- `App` 现有主要数据流
- 路由入口数量
- 主要业务流程与权限边界

### 允许调整

- TSX 结构重组
- 新增全局样式入口
- 新增 CSS variables 和通用类
- 重组页面布局层级
- 为若干组件补充语义化 className
- 适度抽取可复用的展示组件

### 暂不做

- 引入大型 design system
- 引入状态管理库
- 重做数据请求模型
- 增加复杂图表

## 测试与验证

本轮完成后至少需要覆盖：

- 前端构建通过
- 现有前端测试通过
- 关键页面在开发态和静态构建态下可正常渲染
- 登录页、集群列表、详情页、Advanced 编辑页无明显布局断裂

如果当前测试覆盖不足，允许补充少量以结构为主的 UI 测试，但不把测试范围无限扩大。

## 风险与约束

### 1. 当前组件粒度较粗

部分页面目前在单个文件中承担了布局和业务展示双重职责。实现时需要谨慎重组，避免为了样式而把逻辑打散过度。

### 2. 未引入 UI 库意味着样式需自行维护

优点是可控、轻量；代价是需要从 token、布局、组件状态开始自己建立体系。因此本轮必须先搭好基础样式层，而不是继续零散修补。

### 3. 需要控制视觉改造范围

这次目标是让控制台达到“成熟可用”的视觉水位，而不是无限制追求精致像素稿。必须优先保证：

1. 信息顺序正确
2. 操作区清晰
3. 表单与记录面板易读
4. 后续可扩展

## 结论

本轮 UI 重设计将以 `Steel Ops` 为统一视觉方向，对 `control-plane/web` 的登录页、集群列表、集群详情和高级编辑模式进行系统化改造。

这不是简单的样式打补丁，而是在不改变后端协议和核心数据流的前提下，建立一套可持续复用的控制台前端表现层基础。后续无论继续扩展更多管理功能，还是增加新的面板模块，都应复用本轮建立的 token、布局和组件规则。
