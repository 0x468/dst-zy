# DST 控制平面标准闭环设计

## 背景

当前控制平面已经完成一轮 UI 重设计，界面从原始占位页提升到了可长期使用的控制台风格，但功能层仍明显偏轻：

- 能看基础集群列表
- 能做少量状态查看
- 有部分配置编辑入口
- 仍不足以支撑“在面板里新建并长期管理集群”的核心目标

用户已经明确下一阶段目标不是优先解决历史集群迁徙，而是先把“在面板里新建并长期管理集群”做成一个真正可用的闭环。这个方向的核心要求是：

- 在面板里创建一个新的 `Master + Caves` 集群
- 填完表单即可直接启动成可玩的新集群
- 后续继续在同一个面板里做日常运维和配置管理

因此，控制平面的下一阶段应该从“可视化入口”升级为“标准闭环管理系统”。

## 目标

构建控制平面 V2 的第一个真正可用功能闭环，使用户能够：

- 在面板中创建新的 `Master + Caves` 集群
- 完成基础配置、端口配置、认证参数配置
- 直接启动、停止、重启、更新、校验集群
- 查看基础运行日志
- 创建备份并执行基础恢复操作
- 在一个详情页内长期管理该集群

这个闭环的目标不是覆盖所有高级场景，而是先把“新建并长期管理”做扎实。

## 非目标

以下内容不纳入本阶段：

- 历史集群复杂迁徙作为主线目标
- 自动扫描 `data` 目录并批量纳管历史集群
- 图形化 mod 全量管理
- 世界高级参数大全表单
- 多宿主机 / 远程 agent / 多节点编排
- 多租户、复杂 RBAC、SSO
- 高级日志检索、全文搜索、时间范围筛选
- 实时资源监控图表
- 批量多集群联动操作

## 方案比较

### 方案 1：向导式标准闭环

- 用向导创建新集群
- 表单完成后自动生成可运行的 `Master + Caves`
- 详情页承担后续长期管理

优点：

- 最符合“新建并长期管理”的目标
- 用户不需要先理解底层文件结构
- 面板具备真正产品闭环，而不是文件编辑器包装

缺点：

- 后端需要承担更多配置生成与校验逻辑
- 需要明确哪些字段进入向导、哪些延后到详情页

### 方案 2：文件驱动闭环

- 面板主要帮用户生成和编辑底层配置文件
- 运行逻辑仍以“理解文件”为主

优点：

- 实现更快
- 与当前文件体系贴合更紧

缺点：

- 用户仍需要理解很多底层配置
- 很难真正做到“填完就能启动”
- 不足以形成管理产品闭环

### 方案 3：运行时优先闭环

- 优先强化启动、停止、更新、日志等运行时能力
- 新建集群只提供最小配置

优点：

- 运维控制感强
- 风险较低

缺点：

- 新建集群体验仍偏弱
- 与“表单填完即可直接启动”目标不一致

## 选型

选择方案 1：`向导式标准闭环`

原因：

- 用户已明确选择“在面板里新建并长期管理集群”为优先目标
- 用户也已明确选择“表单填完后就能直接启动成一个可玩的新集群”
- 默认世界形态固定为 `Master + Caves`
- 这要求后端必须承担配置生成、校验、运行前检查和启动衔接，而不是仅提供文件编辑界面

## 产品范围总览

第一阶段标准闭环由五个主模块构成：

1. 集群列表页
2. 新建集群向导
3. 集群详情页
4. 日志与任务视图
5. 备份与恢复视图

此外，后端必须同时具备两类隐形能力：

- 预检 / 诊断
- 操作审计

## 模块设计

### 1. 集群列表页

职责：

- 展示所有已纳管集群
- 展示运行状态与关键摘要
- 提供“新建集群”入口
- 作为进入详情页的总导航

至少应展示：

- 显示名称
- slug
- 当前状态
- 最近操作摘要
- 最近更新时间

当前阶段不要求在列表页做复杂批量操作，也不要求在这里承载深度编辑。

### 2. 新建集群向导

这是本阶段的核心新增能力。

目标：

- 用户完成表单后，控制平面自动生成一个可直接启动的 `Master + Caves` 集群
- 若用户选择“立即启动”，则创建后直接进入预检和启动流程

### 向导步骤

建议固定为四步，避免长表单失控：

### Step 1：基础信息

字段：

- 显示名称
- slug
- 集群目录名
- 房间名称
- 房间描述
- 游戏模式
- 最大人数

职责：

- 定义这个集群的身份与房间基本展示信息

### Step 2：网络与运行

字段：

- Master 对外端口
- Caves 对外端口
- Steam 相关端口
- 时区
- 默认启动模式
- 是否创建后立即启动

职责：

- 定义该集群的运行入口和端口边界
- 在向导阶段就进行端口冲突预检查

### Step 3：认证与关键参数

字段：

- 科雷 token / key
- `cluster_key`
- 基础网络可见性参数
- 必要的管理员 / 认证相关字段

职责：

- 保证创建出的集群具备可启动和可连接的关键认证条件

### Step 4：确认与生成

展示：

- 配置摘要
- 端口占用检查结果
- 将要创建的目录和文件
- 是否立即启动

动作：

- 用户确认后执行生成
- 若勾选立即启动，则生成完成后直接触发启动任务

### 3. 集群详情页

这是标准闭环的长期管理主页面。

本阶段详情页应由六个核心卡片区块组成：

### 3.1 状态总览

展示：

- 当前状态
- 集群名称 / slug / 房间名
- 关键端口
- 最近一次操作结果
- 最近一次更新时间

目标：

- 让用户进入详情页后第一眼知道集群当前是否健康

### 3.2 运行控制

操作：

- 启动
- 停止
- 重启
- 更新
- 校验
- 创建备份

目标：

- 集中承载日常最高频运维动作

### 3.3 基础配置

字段建议：

- 房间名称
- 房间描述
- 游戏模式
- 最大人数
- token / key
- 基础网络可见性配置

目标：

- 先覆盖高频配置，不在第一阶段做全量 ini 映射

### 3.4 端口与连接

展示：

- Master / Caves 对外端口
- Steam 相关端口
- 当前映射关系
- 基础连接说明
- 端口异常或冲突提示

目标：

- 明确当前集群如何暴露服务、如何连接

### 3.5 日志与任务

第一阶段日志能力固定为基础版，只分三类：

- 任务日志
- Master 日志
- Caves 日志

先做到：

- 最近日志查看
- 分源切换
- 基础刷新
- 失败时可快速看到错误摘要

不做：

- 全文搜索
- 时间范围筛选
- 下载日志
- websocket 实时流式滚动
- 重型日志索引

### 3.6 备份与恢复

第一阶段要求：

- 手动创建备份
- 列出已有备份
- 恢复某个备份
- 下载备份

目标：

- 让标准闭环具备基本的数据保护能力

### 4. 日志与任务模型

本阶段要明确把“运行日志”和“操作日志”分开。

### 任务日志

面向控制平面动作：

- create-cluster
- start
- stop
- restart
- update
- validate
- backup
- restore

至少记录：

- 操作类型
- 操作发起时间
- 操作结果
- 错误摘要
- 标准输出 / 标准错误摘录

### Master / Caves 日志

面向 DST 运行时输出：

- Master shard 输出
- Caves shard 输出

至少支持：

- 读取最近日志片段
- 手动刷新
- 与任务日志独立展示

### 5. 备份与恢复模型

本阶段先围绕“集群级备份”展开，而不是复杂的细粒度备份。

要求：

- 面板可触发集群备份任务
- 备份记录在 UI 中可见
- 支持下载
- 支持恢复指定备份

恢复操作必须有明确确认机制，并记录审计事件。

### 6. 预检与诊断

这是本阶段必须补齐的后端基础能力，虽然未必全部显性成为单独页面。

至少应检查：

- token / key 缺失
- 端口冲突
- 关键目录或关键文件缺失
- `Master` / `Caves` 必要配置不完整
- 启动前条件不满足

这些检查结果应在以下阶段可见：

- 新建向导确认页
- 详情页状态区
- 启动前任务结果

### 7. 操作审计

必须记录：

- 谁执行了什么操作
- 操作发生时间
- 目标集群是谁
- 操作成功还是失败
- 错误摘要是什么

第一阶段不要求复杂审计筛选，但要求基础可见、可回溯。

## 配置生成与文件落地

为了达成“填完即可启动”，后端必须自动生成并维护以下配置产物：

- 集群元数据记录
- `data/<cluster>/cluster.ini`
- `data/<cluster>/Master/server.ini`
- `data/<cluster>/Caves/server.ini`
- 必要的默认目录结构
- 集群运行所需的 compose / env / runtime 配置

这些文件仍然是真实落地文件，而不是仅存在数据库中的虚拟配置。

## 创建后立即启动流程

如果用户在向导末尾选择立即启动，流程应为：

1. 写入配置与目录
2. 执行预检
3. 创建任务记录
4. 调用运行时管理器执行启动
5. 跳转详情页
6. 在详情页显示启动中的状态、任务日志和后续结果

如果预检失败，则不应假装创建成功后再在后台静默报错，而应直接把失败结果反馈给用户。

## 本阶段明确排除项

以下功能即使用户未来需要，也不应在本阶段提前塞入：

- 图形化 mod 管理器
- `modoverrides.lua` 复杂编辑
- 世界生成高级参数大全
- 历史集群复杂导入导出工作流
- 多集群批量更新
- 多用户权限矩阵
- 实时资源图表

这些功能会显著扩大实现面，应该在标准闭环稳定后再继续拆分。

## 数据与状态边界

本阶段状态来源仍保持混合模式：

- 运行时真实状态来自文件系统、Docker / compose、任务执行结果
- 控制平面数据库保存管理元数据、快照和审计信息

数据库不应该替代文件和运行时成为唯一真相源。

## 风险与难点

### 1. 新建向导的字段边界

字段过少会导致“创建后仍不可玩”，字段过多又会让向导退化成长表单地狱。

本设计通过四步向导和“高频字段先做、高级字段后移到详情页”的方式控制复杂度。

### 2. 端口与运行时语义

DST 端口、分片端口、Steam 相关端口和宿主机映射关系容易混淆，因此详情页必须单独设置“端口与连接”区块，避免用户继续在 compose、ini 和面板之间来回猜。

### 3. 日志能力的边界控制

日志功能很容易无限膨胀，因此本阶段只做基础版：

- 分源
- 最近日志
- 手动刷新
- 错误摘要

先不进入搜索、索引、下载、实时流。

### 4. 备份恢复的安全性

恢复操作天然高风险，因此必须：

- 要求显式确认
- 写入审计
- 明确反馈成功或失败结果

## 结论

控制平面的下一阶段应以“向导式标准闭环”为目标版本，先把“在面板里新建并长期管理 `Master + Caves` 集群”做成真正可用的产品能力。

这一阶段的成功标准不是功能列表更长，而是以下事情真的成立：

- 用户在面板里创建新集群
- 表单填完即可直接启动
- 启停、更新、校验、日志、备份、恢复都能在同一控制台完成
- 关键错误能被预检和审计捕获

做到这一点之后，后续再进入迁徙、mod 管理、高级世界配置等更复杂方向，整个产品才有稳固基础。
